## 2. Паспорт архива `vote-master.zip`

### 2.1. Объём и структура

- ZIP: 851,4 МБ; распакованный объём ~9,5 ГБ; **102 320 JSON-файлов**.
- Шаблон пути: `vote-master/poll/YYYY-MM-DD/{id}.json`, где `YYYY-MM-DD` — дата голосования, `{id}` — идентификатор голосования на сайте.
- Первый файл: `poll/1994-01-11/18642.json`; последний: `poll/2024-03-13/126287.json`.
- Формат файлов: UTF-8, табуляция для отступов, LF, пустая строка в конце (эталон формата — файлы репозитория; прототип парсера воспроизводит его намеренно).

```json
  "datetime": "2024-03-13T15:01:13+0300",

      "deputy": {
        "id": "99113478",

        "faction": { "id": "72100024", "title": "ЕР" }

      "result": "accept"

}
```

### 2.3. Особенности и аномалии (проверено)

1. **Идентификаторы уникальны, но не монотонны по времени.** 102 320 уникальных id, дубликатов нет, id внутри файла всегда совпадает с именем файла. Однако диапазоны созывов пересекаются (III созыв содержит id от 2 до 61253; V начинается с 42079). **Нельзя** строить инкрементальный импорт по правилу «id больше последнего» — только обход листингов по созывам и датам.
2. **Пустые голосования:** 78 файлов с `votes: []` (преимущественно 2002–2003 гг., процедурные предложения, напр. `17470.json`: «предл деп Билалова: перейти к п 31»). Импортировать как голосования без результатов; в аналитике исключать (деление на ноль).
3. **Часовые пояса:** `datetime` содержит смещение `+0300` (59 179 файлов) или `+0400` (43 141 файл) — историческое московское время (летнее/зимнее до 2011, постоянное +0400 в 2011–2014, +0300 с 2014). Смещение **сохранять**, хранить как `timestamptz`; не хардкодить +0300 при чтении архива.
4. **Пробелы в архиве** (архив неполон, парсер обязан их закрыть):
   - VI созыв: данные обрываются 24.06.2016 (созыв работал до 04.10.2016);
   - VII созыв: обрыв 17.06.2021 (созыв работал до 11.10.2021);
   - VIII созыв: обрыв 13.03.2024 (созыв работал до сентября 2026);
   - IX созыв (с 30.09.2026): в архиве отсутствует полностью.
5. **Депутаты:** id депутата стабилен между созывами (в выборке 858 из 2294 депутатов встречаются более чем в одном созыве) — один человек = одна запись `Deputy`, членство во фракциях историческое. В VIII созыве за период встречается **465 уникальных депутатов** при 450 мандатах — есть ротация (выбытие/назначение).
6. **Фракции:** id фракции в основном стабилен (КПРФ `72100004`, ЛДПР `72100005`, ЕР `72100024`, «Вне фракций» `72100011`), но **меняется между созывами** у СР: `72100025` (СР-Р, IV) → `72100027` (СР, V–VII) → `72100029` (СР, VIII). Названия тоже меняются («Е-ЕР»/«О-ЕР» в III → «ЕР» с IV). Нужна модель «каноническая фракция + исторические периоды (site-id, название, созыв)».

Нормализатор Э2 использует расширенный шаблон `№\s*(\d{1,10}-\d{1,2})` (в архиве есть 8-значные номера старых созывов, например 90040257-3, и двузначные суффиксы) — **20 932** уникальных номера; именно они хранятся в справочнике законопроектов и сверяются `verify`. Доля голосований с номером: I–II — 0%, III — 14,9%, IV — 56,8%, V — 63,7%, VI — 71,4%, VII–VIII — 75,5%. 8. **Стадии** пишутся разнобойно — нужна нормализация по словарю вариантов. Топ префиксов (весь архив): «первое чтение» (10 966), «2 чтение таб. 1 принятые поправки» (3 635), «третье чтение» (3 040), «2 чтение» (2 628), «второе чтение» (2 112), «в целом» (1 678), «за основу» (1 557), «2 чтение таб. 2 отклонённые поправки» (1 465), «3 чтение» (1 329), «1 чтение» (970), «к отклонению» (361), а также «1 чт», «табл 1», «таблица 1», «вернуть во 2 чтение» и т.п.
9. **Длина заголовка:** максимум **1154** символа (полный проход архива 14.11.2026; 2 379 заголовков длиннее 512; прежнее значение 378 — устарело). Хранить `text` без ограничения длины; для поискового индекса — полный заголовок.
10. Оценка пользователя «135712 − 115580 = 20132 записей о законопроектах VIII созыва» — это диапазон **id всех голосований** VIII созыва на сайте (не только законопроектов); законопроекты составляют ~75,5% из них. На 12.11.2026 максимальный id VIII созыва на сайте — 135716.

## 3. Живой сайт `vote.duma.gov.ru`

Доступен по HTTP (проверено 12.11.2026: корень, карточки, листинги — 200). Официального API нет; данные извлекаются из HTML.

### 3.1. Листинг

- URL: `http://vote.duma.gov.ru/?convocation={код}&number={номер}&faction={id}&deputy={id}&sort={date|result_desc}&page={n}`.
- **20 элементов на страницу**; элементы сгруппированы по датам (`div.date-head > div` = «ДД.ММ.ГГГГ»).
- Элемент: `div.item` → `div.item-left` (время, ссылка `href="/vote/{id}"` с текстом-заголовком) и `div.item-right` (итог: `<div class="green"><b>Принят</b> <span>|</span> За: 419 чел (93%)</div>`, ниже «Против: 0, Воздержалось: 0»). Цветовой класс отклонённых голосований уточняется на этапе разработки парсера (в проверенных выборках встречался только `green`/«Принят»).
- Фильтры формы: `convocation` (select), фракция (select, id фракций текущего созыва), депутат (select, id депутатов), `number` (номер законопроекта), сортировка «По дате» / «По результатам» (`sort=result_desc`).
- Пагинация: ссылки `page=N`; на последней странице элементов может быть меньше 20.

Подписи сайта — ориентировочные годы; принадлежность голосования созыву определяется **датой голосования** по фактическим границам. В карточке голосования сайт сам отдаёт код созыва в ссылках (`convocation=AAAAAAA8`) — использовать его как основной источник, дату как проверочный.

Состояние на 12.11.2026:

- VIII созыв на сайте: максимальный id **135716**, последняя страница листинга **835** → порядка **16,7 тыс. голосований** (в архиве только 8 790 — разрыв ~7,9 тыс. голосований за 14.03.2024–29.09.2026 закрывает парсер).
- IX созыв: первое голосование **135981** от 30.09.2026 12:57:17 («О проекте постановления Государственной Думы "Об обеспечении деятельности депутатов ГД…"»); на 12.11.2026 — 22 страницы, ~**437 голосований**, максимальный id **136416** (12.11.2026).
- Несуществующие id (например, 135717, 135800 — «дырки» между созывами) отвечают **HTTP 500**. Парсер обязан отличать «нет такого голосования» от временной ошибки (ретраи с backoff).

### 3.3. Карточка голосования `/vote/{id}`

- Заголовок: `<h1>` (с декодированием HTML-сущностей, напр. `&quot;`).
- Дата: `div.date-p > span` = «13.03.2024 15:01:13» — московское время без указания пояса; для новых голосований (с 2014) это +0300.
- Голоса депутатов «зашиты» в `<script>`: переменная **`deputiesData`** — JSON-массив. Пример записи (проверено на `/vote/126282`, 447 записей):

```json
{
  "letter": "А",
  "name": "<span><b class=\"t\">Абакаров</b> Хизри Магомедович</span>",
  "sortName": "Абакаров Хизри Магомедович",
  "url": "/?convocation=AAAAAAA8&deputy=99113478",
  "faction": "ЕР",
  "factionCode": "72100024",
  "result": "for"
}
```

- Поля: `name` содержит HTML-теги (фамилия выделена `<b>`), `sortName` — чистое ФИО (предпочитать его, либо чистить `name` от тегов и схлопывать пробелы — баг «АбакаровХизри» из прототипа); id депутата извлекается из `url` (`deputy=(\d+)`); фракция — `factionCode` (id) + `faction` (короткое название).
- Коды результатов живого сайта: `for`, `against`, `abstain`, `absent`. Маппинг в канонические:

| Сайт | Канон | Смысл |
|---|---|---|
| `for` | `accept` | За |
| `against` | `decline` | Против |
| `abstain` | `abstain` | Воздержался |
| `absent` | `none` | Не голосовал |

- Итог голосования («Принят»/«Отклонён», счёт «За») на карточке отдельным блоком не найден — он есть в **листинге**. Парсер собирает итог из элемента листинга при обходе; для голосований, импортированных только из архива, итог неизвестен (`null`) и может быть вычислен позже по правилам подсчёта (см. [04-functionality.md](04-functionality.md), §2.4).

### 3.4. Правила вежливого обхода

- Последовательные запросы, пауза ≥ 0,5–1 с (1–2 req/s), экспоненциальный backoff при 5xx/таймаутах, разумный `User-Agent`, проверка `robots.txt` перед первым обходом.
- Полный обход VIII+IX созывов ≈ 17,2 тыс. карточек + ~860 страниц листингов → при 1 req/s порядка 5–6 часов; обход возобновляемый (журнал прогресса), идемпотентный.

## 4. Прототип `GosDuma/parsing.py` — что переносим и что исправляем

Алгоритм прототипа (подтверждён рабочим прогоном на `/vote/126282`):

1. GET страницы с `User-Agent`; кодировка UTF-8.
2. id — из URL; заголовок — `<h1>`; дата — `div.date-p > span`, формат `%d.%m.%Y %H:%M:%S` → ISO 8601.
3. Regex `deputiesData\s*=\s*(\[.*?\]);` (DOTALL) → JSON-массив.
4. Для каждого депутата: id из `url`, очистка ФИО от тегов + схлопывание пробелов, маппинг результата, фракция из `factionCode`/`faction`.
5. Сборка JSON в формате репозитория (табы, LF, финальный перевод строки).

Исправления при переносе в C#:

| Прототип | В DumaLens |
|---|---|
| Хардкод `+0300` | Для живых страниц — +0300 (Москва с 2014); для архива — парсить смещение из `datetime` (+0300/+0400) |
| Один URL, без листинга | Кроулер листингов по созывам + очередь карточек |
| Нет ретраев и журнала | Retry/backoff, журнал прогресса, возобновление |
| Нет итога голосования | Итог («Принят»/«Отклонён», счёт) из листинга |
| Нет валидации | Проверки: число депутатов 430–460, известные коды результатов, непустой заголовок; аномалии — в карантин, не в основную базу |

## 5. Риски данных

| Риск | Митигация |
|---|---|
| Сайт изменит вёрстку/`deputiesData` | Парсер изолирован в отдельном проекте; тесты на сохранённых HTML-фикстурах; алерт при резком падении числа извлечённых записей |
| HTTP 500 на несуществующих id | Классификация ошибок: 500/404 после N ретраев → «id отсутствует», не ронять обход |
| Пробелы и пересечения id в архиве | Импорт по уникальному id (upsert), сверка контрольных сумм §2.2; добор пробелов листингами |
| Смена id/названий фракций между созывами | Канонические фракции + исторические периоды; справочник собирается при импорте, новые значения — в лог |
| Ротация депутатов (465 > 450) | `Deputy` по site-id; членство во фракции — по периоду/созыву, не «навсегда» |
| Пустые и процедурные голосования | Флаг `hasResults`; исключение из процентной аналитики |
| Потеря данных при повторном импорте | Upsert по id + транзакции; сырые снапшоты (опция) для переимпорта |
