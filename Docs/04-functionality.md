# 04 — Функциональность DumaLens

Детализация требований ТЗ ([03-tz.md](03-tz.md)): формулы фракционной аналитики, конструктор фильтров, поиск, нормализация, теги, рейтинги, контракт API и страницы интерфейса.

## 1. Позиция фракции: формулы и семантика

### 1.1. Исходные величины

Для каждого голосования и каждой фракции из индивидуальных голосов депутатов вычисляются:

| Величина | Определение |
|---|---|
| `acceptCount` | число депутатов фракции с результатом `accept` (За) |
| `declineCount` | число с `decline` (Против) |
| `abstainCount` | число с `abstain` (Воздержался) |
| `noneCount` | число с `none` (Не голосовал) |
| `memberCount` | `acceptCount + declineCount + abstainCount + noneCount` — все депутаты фракции, присутствующие в записи голосования (состав фракции на момент голосования) |
| `votedCount` | `acceptCount + declineCount + abstainCount` — фактически голосовавшие |

### 1.2. Две базы процента

```text
pctMembers(result) = count(result) / memberCount      // от состава фракции
pctVoted(result)   = count(result) / votedCount        // от проголосовавших; result ∈ {accept, decline, abstain}
```

- **От состава (`members`)** — основной показатель позиции фракции: не голосовавшие снижают долю. Пример: в НЛ 15 депутатов, За — 12, не голосовали — 3 → `pctMembers(accept) = 12/15 = 80%`.
- **От проголосовавших (`voted`)** — дополнительный: показывает расклад среди реально голосовавших (12/12 = 100%). Может искажать картину при малой явке, поэтому для позиции фракции по умолчанию используется `members`. Доступен только для `accept`/`decline`/`abstain`: «не голосовал» в базу `voted` не входит, поэтому для `none` существует единственная база — `members`.
- Проценты хранятся как `numeric(5,2)` в диапазоне 0,00–100,00 (вычисляются один раз при импорте, не на лету). Всего 7 процентных колонок: 4 от состава (`accept/decline/abstain/none`) и 3 от голосовавших (`accept/decline/abstain`). Колонки «не голосовал от проголосовавших» нет: `noneCount/votedCount` — не доля (значение >100, до 34 200 на архиве) и аналитически избыточно — однозначно выводится из `NonePctMembers`; для анализа неучастия/бойкота используются `NonePctMembers` и `NoneCount`.
- Если знаменатель равен 0 (фракции нет в голосовании; пустое голосование) — процент `NULL`, условие по такой фракции не выполняется.

### 1.3. Условие по фракции

Условие = кортеж `(faction, result, operator, threshold, basis)`:

- `faction` — каноническая фракция (ЕР, КПРФ, ЛДПР, СР, НЛ, …; исторические названия резолвятся в канон);
- `result` ∈ {`accept`, `decline`, `abstain`, `none`};
- `operator` ∈ {`gte` (≥), `lte` (≤)};
- `threshold` — 0–100 (шаг 0,1);
- `basis` ∈ {`members`, `voted`}; для `result=none` допустима только `members` (комбинация `none+voted` не поддерживается, §1.2; в API — `422`).

Пример: `(НЛ, accept, gte, 70, members)` — «НЛ голосовала ЗА не менее чем 70% состава».

**Интерпретация «фракция проголосовала ЗА»**: по умолчанию — `pctMembers(accept) ≥ threshold`. Предустановки порога: 50% (простое большинство), 66,7% (квалифицированное), 90% (консолидированная позиция), 100% (единогласно). Порог и база задаются в каждом запросе.

### 1.4. Комбинации условий

- Несколько условий объединяются логическим **И** (каждое — своя фракция/результат/порог/база).
- Поиск расхождений — частный случай: `(НЛ, accept, gte, 70, members) AND (КПРФ, decline, gte, 50, members)`.
- «Фракция НЕ ЗА» выражается как `(faction, accept, lte, X)` с нужным порогом либо через условие на `decline`/`abstain`/`none` — отдельного оператора «не» на MVP нет (осознанное упрощение).
- Условия по одной фракции с разными результатами допустимы (например, «ЕР: За ≥ 60% И Против ≤ 10%»).
- Голосования без результатов (`HasResults = false`, 78 пустых в архиве) не попадают в выдачу фракционных условий.

### 1.5. Вычисление и производительность

- Агрегаты считаются **при импорте** и хранятся в таблице `VoteFactionStats` (одна строка на голосование × фракцию): counts + оба набора процентов + `memberCount`/`votedCount`.
- Фракционный фильтр — это SQL по агрегатам (EXISTS/JOIN на каждую фракцию условия), без сканирования 45 млн индивидуальных голосов. Индексы — см. [05-architecture.md](05-architecture.md) §4.
- Индивидуальные голоса хранятся полностью (для карточек и аналитики депутатов), но в горячем пути поиска не участвуют.
- Пересчёт агрегатов: команда `recalc-stats` (после исправления данных/карантина); при обычном импорте агрегаты строятся сразу.

## 2. Нормализация заголовков

### 2.1. Номер законопроекта

- Regex: `№\s*(\d{4,7}-\d)` (первое вхождение). Пример: `(третье чтение) О проекте федерального закона № 500091-8 "О внесении изменений..."` → `500091-8`.
- Номер уникален в справочнике законопроектов; голосования без номера — процедурные (`BillId = null`).
- Варианты написания («N 500091-8», «№500091-8» без пробела) покрываются regex; экзотические случаи фиксируются в карантин нормализации для ручного разбора.
- В архиве 17 608 уникальных номеров; доля голосований с номером растёт от 0% (I–II созывы) до 75,5% (VII–VIII).

### 2.2. Стадия

Нормализованный enum `VoteStage` + словарь вариантов (регистронезависимо, по началу заголовка):

| Канон | Варианты в данных |
|---|---|
| `FirstReading` | «первое чтение», «1 чтение», «1 чт», «в первом чтении» |
| `SecondReading` | «второе чтение», «2 чтение» (без уточнения таблицы) |
| `SecondReadingAcceptedAmendments` | «2 чтение таб. 1 принятые поправки», «табл 1 прин поправок», «таблица 1» (в контексте 2 чтения) |
| `SecondReadingRejectedAmendments` | «2 чтение таб. 2 отклонённые поправки», «2 чтение таб. 2 отклоненные поправки», «табл 2» |
| `ThirdReading` | «третье чтение», «3 чтение» |
| `AsBasis` («за основу») | «за основу» |
| `AsWhole` («в целом») | «в целом» |
| `Reject` («к отклонению») | «к отклонению» |
| `ReturnToSecondReading` | «вернуть во 2 чтение», «вернуть во второе чтение» |
| `Procedural` | порядок работы, регламент, предложения депутатов («предл деп …»), постановления без номера |
| `Unknown` | всё остальное — исходный префикс сохраняется в `StageRaw` |

Правила: сначала ищется номер законопроекта; стадия определяется по словарю; при конфликте (несколько совпадений) — приоритет более специфичного варианта («2 чтение таб. 1…» важнее «2 чтение»). Словарь хранится в коде (тесты на каждый вариант) и расширяется по журналу `Unknown`.

### 2.3. Очистка заголовка

- Декодирование HTML-сущностей (`&quot;`, `&amp;`, …) — для данных с живого сайта.
- Схлопывание пробелов, обрезка краёв; исходный заголовок сохраняется без потерь (макс. длина в архиве — 1154 символа; колонка `text` без ограничения, паспорт данных 02 §2.3.9).
- Ведущие служебные маркеры сайта «*»/«**» (повторные голосования по отклонённым законопроектам) снимаются с очищенного заголовка (regex `^[\s*]+`); для разбора стадии они также игнорируются. Накопленные заголовки приводит к очищенному виду команда `normalize-titles` (идемпотентно).
- ФИО депутатов: `sortName` с сайта либо очистка `name` от тегов (`<b>`, `<span>`) + схлопывание пробелов (фикс бага «АбакаровХизри»).

### 2.4. Итог голосования

- Факт с сайта (листинг): «Принят»/«Отклонён» + счёт «За: N чел (P%)». Хранится как `Outcome` (`Accepted`/`Rejected`/`Unknown`) и `AcceptCountTotal`/`AcceptPercentSite`.
- Для архивных записей итог `Unknown`. Расчётный итог по правилам подсчёта (простое/квалифицированное большинство от 450) — **отдельное поле-оценка** `ComputedOutcome`, помеченное как расчётное; на MVP не вычисляется (требует знания требуемого большинства для каждого типа вопроса), отложено.
- Итог из листинга доступен только для голосований, пройденных кроулером; для архива он добирается при обходе листингов соответствующего созыва (листинг отдаёт все голосования созыва, включая старые).

## 3. Поиск

### 3.1. Полнотекстовый поиск

- PostgreSQL FTS: колонка `TitleSearch tsvector` (генерируемая, `to_tsvector('russian', title)`), индекс GIN.
- Запрос пользователя → `to_tsquery('russian', …)` с префиксными лексемами (`слово:*`); текст tsquery строит `RussianTsQueryBuilder` (Э5): слова через пробел = И, `"фраза"` = соседство, `-слово` = НЕ, `OR`/`|` = ИЛИ. Выбор зафиксирован на Э5: `websearch_to_tsquery` отклонён — он не объединяет существительные и прилагательные (алкоголя → алкогол, алкогольной → алкогольн), из-за чего поиск «алкоголь» не находил законопроект 500091-8 (П-4): на полном архиве 2 совпадения против 530 у префиксного поиска. Префикс `алкогол:*` покрывает обе лексемы; морфологию выполняет PostgreSQL, построитель только расставляет операторы и очищает ввод от служебных символов tsquery.
- Ранжирование: `ts_rank` по релевантности; при пустом запросе — сортировка по дате.
- Поиск по номеру законопроекта — отдельный точный фильтр (не FTS).

### 3.2. Фильтры (комбинируются И)

| Фильтр | Параметр API | Семантика |
|---|---|---|
| Текст | `q` | FTS по заголовку |
| Созыв | `convocation` | номер 1–9 (резолвится в код сайта) |
| Период | `dateFrom`, `dateTo` | дата голосования включительно (московское время) |
| Законопроект | `billNumber` | точное совпадение номера |
| Стадия | `stage` | каноническое значение enum |
| Итог | `outcome` | accepted / rejected / unknown |
| Только с результатами | `hasResults` | по умолчанию true для фракционных условий |
| Фракционные условия | `factionConditions` | массив кортежей §1.3, И |
| Депутат + его результат | `deputyId`, `deputyResult` | v1.1 |
| Теги / рейтинг | `tags`, `minImportance` | v1.1/v1.2 |

### 3.3. Сортировка и пагинация

- `sort`: `dateDesc` (по умолчанию), `dateAsc`, `relevance` (при непустом `q`), `acceptCountDesc`.
- `page` (с 1), `pageSize` (по умолчанию 20, максимум 100). Ответ содержит `totalCount`, `page`, `pageSize`.
- Стабильная сортировка: при равенстве ключа — по id.

### 3.4. Примеры запросов (из замысла)

1. «В каких записях НЛ проголосовала ЗА ≥ 70%»: `factionConditions=[(НЛ, accept, gte, 70, members)]`.
2. «НЛ ЗА ≥ 70%, КПРФ ПРОТИВ ≥ 50% — где различия»: два условия И, базы независимы.
3. «Все третьи чтения по 500091-8»: `billNumber=500091-8&stage=ThirdReading`.
4. «Голосования VIII созыва про алкоголь, где ЕР не единогласна»: `q=алкоголь&convocation=8&factionConditions=[(ЕР, accept, lte, 99.9, members)]`.

## 4. Теги и важность (v1.1–v1.2)

### 4.1. Теги

- Справочник: `slug`, `title`, `category` (theme/assessment), `sentiment` (positive/negative/neutral), `description`.
- Стартовый набор из замысла: «Укрепление законодательного статуса регионов в зоне действия СВО» (theme, positive), «Репрессивная поправка» (assessment, negative), «Увеличение штрафа» (assessment, negative), «Защита прав граждан» (theme, positive), «Экономическое регулирование» (theme, neutral), «Регулирование алкогольной продукции» (theme, neutral).
- Привязка к голосованию и/или законопроекту; источник `manual` / `auto_keyword`; статус `pending` / `approved` / `rejected`; автор, дата. В выдаче поиска участвуют только `approved`.
- Правила автотегирования: regex по заголовку → тег `pending`; пример правила: `увеличен(ие|ия)? штраф` → «Увеличение штрафа». Массовое применение — команда CLI; модерация — approve/reject в интерфейсе (v1.1, роль Модератор; аутентификация вводится на Э9 — [07-security.md](07-security.md)).
- ML-тегирование — v2+, вне текущего ТЗ.

### 4.2. Важность

- Экспертная оценка 0–10 (роль Модератор), пользовательские 1–5 (роль Пользователь, по одной на пользователя на законопроект).
- Агрегаты: `expertScore`, `publicScore = AVG(оценок)`, `votesCount`.
- Итоговый байесовский рейтинг: `finalScore = (C·m + Σs) / (C + n)`, где `m` — средняя оценка по всему сайту, `C` — вес (по умолчанию 10, конфигурируется). Смысл: законопроект с одной оценкой «5» не обгоняет законопроект с 1000 оценок «4,8».
- Рейтинг привязан к **законопроекту** (не к отдельному голосованию): голосования наследуют рейтинг законопроекта для фильтров/сортировки.

## 5. Контракт REST API (MVP)

Базовый префикс `/api`. Хост — `DumaLens.Api`; Web обращается к нему по HTTP через `DumaLens.Api.Client`. Формат — JSON; ошибки — единый `ApiExceptionDetail` (код, сообщение, детали валидации). Все эндпоинты чтения — публичные (`[AllowAnonymous]`); auth-эндпоинты — §5.4 и [07-security.md](07-security.md).

### 5.1. Поиск голосований

```http
GET /api/votes?q=алкоголь&convocation=8&dateFrom=2021-10-12&dateTo=2026-09-29
    &billNumber=500091-8&stage=ThirdReading&outcome=accepted
    &sort=dateDesc&page=1&pageSize=20
    &factionConditions[0].faction=NL&factionConditions[0].result=accept
    &factionConditions[0].operator=gte&factionConditions[0].threshold=70
    &factionConditions[0].basis=members
```

Ответ `200`:

### 5.2. Карточки и справочники (реализовано на Э6)

JSON — camelCase; enum-ы (`stage`, `outcome`, `result`, `source`) сериализуются строковыми
токенами имён членов (`ThirdReading`, `Accepted`, `Accept`, `Archive`). Проценты — `decimal?`,
null при нулевом знаменателе; `NonePctVoted` не существует (§1.2). Даты границ — `DateOnly`
в московском времени. operationId в OpenAPI — `{controller}_{action}`.

| Эндпоинт | Ответ |

Группировка по канонической фракции; депутаты без фракции — отдельная группа с `factionCode`/`factionTitle` = null, идёт последней. Если в созыве несколько периодов одной фракции (Е-ЕР/О-ЕР, III созыв), заголовок группы — название периода большинства депутатов, при равенстве — ordinal-сравнение (детерминированно). `404` — нет голосования |

### 5.3. Служебные (не HTTP)

```text
dumalens import-archive --zip <путь> [--batch 500] [--resume]

```

### 5.4. Аутентификация и пользователи (база, Э9 — реализовано)

Полная спецификация — [07-security.md](07-security.md); реализация — [13-e9-auth.md](13-e9-auth.md). Контракт:

| Эндпоинт | Доступ | Назначение |
|---|---|---|
| `POST /api/auth/login` | анонимно | пара токенов (access JWT + refresh) + профиль; rate limit |
| `POST /api/auth/refresh` | refresh-токен | ротация пары токенов |
| `POST /api/auth/logout` | аутентифицирован | отзыв refresh |
| `GET /api/auth/me` | аутентифицирован | профиль: id, login, name, роль |
| `POST /api/auth/change-password` | аутентифицирован | смена пароля (меняет SecurityStamp) |
| `GET/POST/PUT /api/users`, `POST /api/users/{id}/reset-password` | Администратор | управление пользователями и ролями |

### 5.5. v1.1/v1.2 (контракт уточняется на этапе)

- `POST /api/bills/{number}/ratings` (оценка пользователя), `GET /api/bills/{number}/rating`.

## 6. Веб-интерфейс (MVP)

**Blazor Server** в `DumaLens.Web` — отдельный фронтенд-хост, ходит в Api по HTTP через NSwag-клиент; без Node.js (ограничение О-5). Интерфейс на русском. Защищённые разделы — `AuthorizeView` по ролям (база auth с Э9).

| Страница | Содержимое |
|---|---|
| `/` (главная) | Строка поиска, сводка массива (голосований, депутатов, период), быстрые ссылки на созывы, примеры запросов |
| `/search` | Панель фильтров: текст, созыв, период, номер законопроекта, стадия, итог; **конструктор фракционных условий**: добавить условие → фракция (select) + результат (select) + оператор (≥/≤) + порог (слайдер 0–100 с предустановками 50/66,7/90/100) + база (переключатель «от состава / от проголосовавших»; для «не голосовал» доступна только «от состава»); выдача карточек-строк с итогом и мини-таблицей фракций; пагинация; состояние фильтров в URL (шаринг ссылки) |
| `/votes/{id}` | Карточка голосования: заголовок, дата, созыв, законопроект, стадия, итог; таблица «фракция × За/Против/Воздержался/Не голосовал» с процентами (от состава — все, от голосовавших — кроме «не голосовал»); список депутатов по фракциям с цветовой индикацией результата |
| `/bills/{number}` | Хронология голосований законопроекта: дата → стадия → итог → позиции фракций; ссылка на СОЗД |
| `/factions`, `/factions/{code}` | Справочник и карточка фракции с историей названий |
| `/deputies`, `/deputies/{id}` | Список депутатов по созыву и карточка депутата: фракции по созывам, участие, личные счётчики |
| `/convocations` | Список созывов с числом голосований (ссылки на поиск по созыву) |

Дизайн: нейтральный, табличный, без тяжёлых зависимостей (один CSS-файл на дизайн-токенах, минимум JS — слайдеры и конструктор условий). Две темы (светлая и тёмная) с переключателем и сохранением выбора. Цвета результатов: За — зелёный, Против — красный, Воздержался — жёлтый, Не голосовал — серый. Полная спецификация стиля, токенов и архитектуры страниц — [12-e8-ui.md](12-e8-ui.md).
