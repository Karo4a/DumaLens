## Э0. Каркас решения

**Задачи:**

1. `DumaLens.sln` + проекты по §1 архитектуры (все `net8.0`); папки `src`/`tests` не используем — плоская структура как в эталоне (проекты в корне решения).
2. `global.json` — пин SDK 8.0.x (`rollForward: latestFeature`); локальный инструмент `dotnet-ef` 8.x в `.config/dotnet-tools.json`.
3. `Directory.Build.props` по образцу эталона (Nullable, ImplicitUsings, тестовые пакеты по условию `*.Tests`) + `Directory.Packages.props` (централизованные версии пакетов, паттерн Specular); `AGENTS.md` с конвенциями репозитория.
4. `.editorconfig` — копия из DocumentGenerator **master** (file-scoped, CRLF); `.gitattributes` (`* text=auto`, `*.cs text eol=crlf`); `.gitignore` (bin/obj/.vs/TestResults).
5. `DumaLens.Common`: `IDateTimeProvider`/`DateTimeProvider`, `RegisterAssemblyInterfacesAssignableTo<T>` (DI по анкерам).
6. `DumaLens.Entities.Contracts`: `DbBaseEntity`, интерфейсы аудита/soft-delete; `DumaLens.Context.Contracts`: `IReader`, `IWriter`, `IDbWriter<T>`, `IUnitOfWork`, `BaseWriteRepository<T>`.
7. Два хоста: `DumaLens.Api` — `Program.cs` по образцу эталона (Npgsql, DI по анкерам, AutoMapper, FluentValidation, Swagger c XML, `DumaLensExceptionFilter`, `EnvironmentProvider`, health-check); `DumaLens.Web` — Blazor Server-хост по образцу DocumentGenerator.Web (`AddInteractiveServerRenderMode`, Components). На Э0 — только health на обоих, контроллеров нет.
8. Тестовая база: `DumaLens.Context.Tests` с `DumaLensContextInMemory`; `DumaLens.Api.Tests` с `TestWebApplicationFactory` (PostgreSQL, ADR-3) + `DependenciesTests`.
9. CI-скрипт (локальный `build.cmd`/`build.ps1`): restore → rebuild → test → `dotnet format --verify-no-changes`.

**Критерии приёмки:**

- Решение открывается в VS 2022, `dotnet build -t:Rebuild` — 0 ошибок/новых warning'ов; `dotnet test` зелёный (пустой набор тестов + DependenciesTests проходят).
- `dotnet format --verify-no-changes` — без изменений.
- Ревью кода: блокирующих замечаний нет.

## Э3. Импорт архива

**Задачи:**

1. `DumaLens.Importer` (System.CommandLine): команда `import-archive --zip --batch --resume`.
2. Потоковое чтение ZIP (без распаковки на диск), последовательная обработка; прогресс в журнал (файл + stdout).
3. Upsert голосований по `SiteId`; построение справочников на лету: депутаты (SiteId → запись), фракционные периоды (SiteId+созыв → период, канон по названию), законопроекты (номер → Bill), членство депутатов.
4. Пакетная вставка `DeputyVotes` через `NpgsqlBinaryImporter` (COPY); транзакции по батчам; при сбое — `--resume` пропускает обработанные id.
5. Карантин аномалий (78 пустых — не карантин, а `HasResults=false`; карантин — только нарушения валидации).
6. Команда `verify`: контрольные суммы по созывам и кодам результатов против паспорта (02, §2.2); отчёт.
7. Интеграционный тест импорта на мини-архиве (фикстуры Э2, ZIP в памяти) + тест идемпотентности (двойной прогон).

**Критерии приёмки (полный прогон на реальном архиве):**

- `verify`: 102 320 голосований; 45 593 720 голосов депутатов; суммы по созывам и кодам результатов совпадают с паспортом **точно**.
- Повторный `import-archive` не меняет суммы (П-2).
- Время импорта ≤ 2 ч (НФТ-02); журнал показывает прогресс и карантин.
- Прерывание + `--resume` завершает импорт без дубликатов (НФТ-04).
- Ревью блокирующих нет.

## Э7. Кроулер живого сайта

**Задачи:**

1. Команда `crawl --convocation N [--from-page] [--delay-ms]`: обход листингов (пагинация до конца), сбор итогов голосований (включая архивные — добор `Outcome`), обнаружение id, отсутствующих в БД.
2. Очередь карточек: пропуск уже импортированных; загрузка `/vote/{id}`, парсинг (Э2), upsert, агрегаты; журнал прогресса, возобновление.
3. Вежливость: пауза ≥ 0,5–1 с (конфигурируемо), backoff при 5xx/таймаутах (3 ретрая), устойчивый 500 → «id отсутствует» в журнал, обход продолжается.
4. Определение созыва по коду сайта; даты IX созыва (с 30.09.2026) — в справочник.
5. Тесты: парсер листинга/карточек уже есть (Э2); интеграционный тест кроулера на локальном HTTP-фикстуре (без реального сайта); тест идемпотентности повторного обхода.
6. Полный обход созывов I–IX на реальном сайте; `verify` после.

**Критерии приёмки (П-5):**

- В БД есть голосования VIII созыва после 13.03.2024 и IX созыва с 30.09.2026; число новых записей соответствует листингам сайта (оценка ~17 тыс.).
- Повторный обход не создаёт дубликатов; устойчивые 500-id зафиксированы в журнале.
- Итоги (`Outcome`) проставлены для голосований, пройденных листингами.
- Ревью блокирующих нет.

## Э9. Аутентификация и роли (база)

Спецификация — [07-security.md](07-security.md); сущности и seed ролей уже с Э1.

**Задачи:**

1. `SecurityHelper`: PBKDF2-SHA256, соль 32 байта, ≥ 100 000 итераций, `FixedTimeEquals` (ADR-12; в эталонах 6 итераций — не копируем).
2. Сервисы Api: `TokenService` (JWT JWS: `sub`/`name`/`role`/`security_stamp`/`jti`, короткий access), `AuthService` (login/refresh/logout/change-password; ротация refresh в БД, повторное использование отозванного → отзыв всех сессий, SecurityStamp).
3. Контроллеры Api: `AuthController`, `UserController` (Администратор: список/создание/роль/блокировка/сброс пароля); JwtBearer middleware, политики иерархии ролей (`RequireRole`), `[AllowAnonymous]` на публичном чтении; rate limiting на логин, счётчик попыток + блокировка.
4. Web: `ClientTokenStore` (ProtectedLocalStorage), `AuthDelegatingHandler` (Bearer + авто-refresh при 401), `UserState`/`UserStateInitializer` + `AuthenticationStateProvider`; форма логина, `AuthorizeView` на защищённых разделах (механика DocumentGenerator.Web).
5. Первый администратор: CLI `dumalens create-admin` (временный пароль → принудительная смена при первом входе).
6. Тесты по 07-security §5: сервисы с реальными репозиториями (без моков), интеграционные 401/403/иерархия ролей/ротация/отзыв.

**Критерии приёмки (П-10):**

- Логин/refresh/logout работают; ротация, отзыв при повторном использовании и смене SecurityStamp проверены тестами.
- Три роли засеяны; Администратор проходит Moderator-эндпоинты; Пользователь получает 403 на админ-эндпоинтах; публичное чтение работает без токена.
- Пароли — PBKDF2 ≥ 100 000 итераций; секретов в репозитории нет (О-7).
- Ревью блокирующих нет.

## Э12. Важность и рейтинги (v1.2)

**Задачи:**

1. `BillImportances`, `ImportanceVotes` + миграции; экспертная оценка 0–10 (роль Модератор), пользовательские 1–5 (роль Пользователь, одна на пользователя).
2. Байесовский рейтинг `(C·m + Σs)/(C + n)`, пересчёт при новой оценке; C/m конфигурируемы.
3. API оценок; фильтр/сортировка поиска по рейтингу (наследование рейтинга законопроекта голосованиями).
4. UI: оценка в карточке законопроекта, сортировка по важности.
5. Тесты: формула (включая кейс «1 оценка 5 vs 1000 оценок 4,8»), уникальность оценки, пересчёт.

**Критерии приёмки:** рейтинг устойчив к малым выборкам; фильтр/сортировка работают; ревью блокирующих нет.

## Сквозные правила (для всех этапов)

1. **Каждый этап** завершается: rebuild без новых warning'ов → тесты → `dotnet format --verify-no-changes` → ревью кода → устранение блокирующих → `dotnet build-server shutdown`.
2. **Тесты пишутся вместе с кодом**, не «потом»: нормализатор/формулы/парсеры — юнит-тесты сразу; API — интеграционные в том же этапе.
3. **Стиль** — `.editorconfig` эталона; при расхождении текстовых конвенций и `.editorconfig` приоритет за `.editorconfig` (ADR-6).
4. **Данные не выдумываются**: все контрольные цифры — из паспорта (02); новые аномалии фиксируются в карантин и журнал, не «чинятся» молча.
5. **Документы обновляются по ходу**: изменения контракта API/модели отражаются в 04/05/07; журнал решений — в §6 архитектуры (новые ADR по мере необходимости).
6. **Секреты** — только конфигурация/переменные окружения; в репозиторий не попадают (О-7).

## Риски и mitigations

| Риск | Вероятность | Митигация |
|---|---|---|
| Сайт меняет вёрстку/`deputiesData` | средняя | Парсеры изолированы в `DumaLens.Parsing`, фикстуры + тесты; при изменении — правка одного компонента; карантин вместо падения импорта |
| Параметры подключения к PostgreSQL не предоставлены вовремя | низкая (уже развёрнут) | Заказчик предоставляет строку подключения на Э0/Э1 (О-7); до этого разработка на локальном PostgreSQL; FTS-стратегия — PostgreSQL (ADR-1) |
| p95 поиска не достигает цели на слабой машине | средняя | Предпосчитанные агрегаты (ADR-7), индексы под фильтры, keyset-пагинация; замер на Э5, не в конце |
| Объём `DeputyVotes` (~53 млн) тормозит импорт | средняя | COPY-вставка батчами, отключение лишних индексов на время первичного импорта с последующим созданием |
| Site-id депутатов/фракций не совпадают между архивом и сайтом | низкая (проверено на VIII) | Сверка на Э3/Э7 по контрольным депутатам; расхождения — в журнал, ручной разбор |

| NSwag-клиент рассинхронизирован с контрактом Api | средняя | Перегенерация клиента после каждого изменения контракта (Э6+); интеграционные тесты Web через клиент ловят расхождение |
