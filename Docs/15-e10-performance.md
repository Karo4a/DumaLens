# 15 — Э10: отчёт о производительности

Замеры нагрузочного прогона Э10 (план Э10, задача 1; НФТ-01/НФТ-03, критерий П-6)
и сценария «поиск во время импорта» (НФТ-11). Дата замеров: 20.11.2026.

## Условия

- **База**: рабочая `dumalens` — 110 780 голосований (102 309 архив + 8 471 сайт),
  49 332 469 индивидуальных голосов, 713 449 строк фракционных агрегатов,
  2 505 депутатов, 24 016 законопроектов; все миграции применены.
- **Хост**: `DumaLens.Api`, сборка Release, запуск `dotnet DumaLens.Api.dll`
  (без отладчика), среда Development, `--urls http://localhost:5299`.
- **Клиент**: консольный стенд (.NET 8), `HttpClient` с keep-alive
  (`SocketsHttpHandler`, пул соединений 5 мин), последовательные запросы;
  время — полный HTTP-круг (запрос → тело ответа), `Stopwatch`.
- **Машина**: эталонная (8 ядер/16 потоков, 32 ГБ, NVMe;
  PostgreSQL 17 локально). Типовая машина ТЗ (4 ядра, 16 ГБ, SSD) слабее;
  запас по p95 ниже покрывает разницу, замеры на слабой машине — импорт/кроул
  ([08-deployment.md](08-deployment.md), тестовая машина).
- **Методика**: на класс запросов — 10 прогревочных + 200 замеряемых
  последовательных запросов; p95 = элемент `ceil(0,95·n)` отсортированной
  выборки (как в приёмках Э5/Э6). Параллельная фаза — 8 воркеров, 60 с,
  классы по кругу; p95/p99 по всем успешным ответам.

## Параллельная нагрузка (8 воркеров, 60 с)

- Запросов: **3 102**, ошибок **0**, пропускная способность **51,5 запр/с**.
- По всем успешным ответам: p50 = 49,3 мс, **p95 = 585,2 мс**, p99 = 795,3 мс,

- Худшие классы по p95: faction-s2 — 863,7 мс; faction-3cond — 856,9 мс;

Нормативы выполнены с запасом; оптимизация (дополнительные индексы, keyset,
кэш справочников) не потребовалась. Планы запросов используют индексы Э4/Э5:
для faction-s2 — `IX_Vote_VotedAt` (parallel index scan backward) +
`PK_VoteFactionStats` (semi-join по EXISTS), сексканов потоковых таблиц нет;
FTS — GIN `IX_Vote_TitleSearch` (подтверждено EXPLAIN в приёмке Э5).
Представительный EXPLAIN (ANALYZE) faction-s2 на текущей базе: выполнение
~0,6 с на холодном кэше при фоновой записи в соседнюю базу, в тёплом виде
через Api — 237–345 мс.

Сравнение с прежними замерами: Э5 — p95 158 мс (сервисный слой, архив
102 309 голосований), Э6 — карточка 18–30 мс (HTTP). Текущие замеры —
сквозной HTTP на выросшей базе (+8 471 site-голосование, агрегаты
662 623 → 713 449); рост p95 фракционных запросов объясняется объёмом
и методом (HTTP против сервисного слоя), норматив соблюдён.

Наблюдения (не дефекты, кандидаты на оптимизацию при росте данных):
- `stats-overview` и `card-faction` — самые тяжёлые карточки (p95 269/194 мс
  последовательно): агрегатные запросы по всем созывам; норматив НФТ-03
  относится к карточке голосования, для них цель не задана.
- `VoteSearchService.BuildFactionIndex` строит индекс резолвинга фракций
  двумя запросами справочников на каждый поиск (25 фракций / 60 периодов —
  дёшево); при росте нагрузки кандидаты — кэш справочников на процесс.

## НФТ-11: поиск во время импорта

Сценарий: одноразовая база `dumalens_e10nft`, **обычный режим** импорта
(пакетные транзакции по 500 голосований, индексы и FK на месте — bulk-режим
не используется: он снимает индексы/FK и предназначен только для пустых таблиц).
Фаза А — `import-archive --max-files 20000` (19 999 голосований за 1:47),
затем Api против этой базы; фаза B — `import-archive --resume` (остальные
82 320 файлов) одновременно с непрерывной смешанной нагрузкой через Api
(4 воркера, те же 21 класс запросов).

Результаты (20.11.2026):

- **Импорт фаза B**: 8 мин 04 с, импортировано 82 310, пропущено 20 000
  (существующие SiteId — без дубликатов), карантин 10 (всего 11 за обе фазы);
  итог по базе: 102 309 голосований, 45 592 378 индивидуальных голосов,
  662 623 строки агрегатов. `verify` после импорта — **24/24**.
- **Нагрузка во время импорта** (4 воркера, 600 с, окно импорта
  20:58:30–21:06:32 UTC): **76 938 запросов, 0 ошибок** (ни одного 5xx/таймаута),
  128,2 запр/с; 9 164 ответа 404 — карточки ещё не импортированных голосований
  (ожидаемо, не ошибки целостности).
- В окне импорта: 69 925 запросов, 60 885 успешных; p50 = 5,8 мс,
  **p95 = 172,3 мс**, p99 = 287,3 мс, max = 697,2 мс. Только поисковые классы:
  46 621 запрос, все 200, **p95 = 107,4 мс**.
- После завершения импорта (полные данные, та же нагрузка): p95 = 252,9 мс.
- Поминутный p95 растёт по мере наполнения базы (39 → 376 мс) — рост объясняется
  объёмом данных, не блокировками: провалов доступности нет, худшая минута
  p95 = 376 мс < 1 с (НФТ-01 соблюдается и под импортом).

Вывод: пакетные транзакции обычного режима (500 голосований + COPY в одной
транзакции) не блокируют читателей — поиск доступен на протяжении всего
импорта, НФТ-11 выполнен. Bulk-режим сценарием не покрывается: он снимает
индексы/FK и требует остановленного Api ([08-deployment.md](08-deployment.md)).

## Выводы

1. НФТ-01 и НФТ-03 выполнены на полном массиве (архив + сайт) с запасом,
   в том числе под параллельной нагрузкой 8 воркеров (П-6).
2. Поиск не блокируется импортом (НФТ-11): пакетные транзакции обычного
   режима не мешают читателям — см. раздел выше.
3. Оптимизация не потребовалась; индексы Э4/Э5/Э8 достаточны на текущем объёме.
